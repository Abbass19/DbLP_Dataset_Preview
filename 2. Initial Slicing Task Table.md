## P1 — Dataset profiling (Task 0)

**~60% done.** Covers DATA-1 through DATA-6 (§8.0):

- **Real, non-obvious finding first:** `dblp.org`'s own `robots.txt`
  disallows crawling for every user agent, and explicitly names
  `Claude-Code` in that disallowed list; its download path also sits
  behind an active Anubis proof-of-work bot wall. I did not attempt to
  script around either. Instead, confirmed (via the dblp project's own
  blog, `blog.dblp.org`) that monthly XML dump hosting moved to the
  Dagstuhl Research Online Publication Server (DROPS) in Dec 2024 — a
  separate, DOI-registered, legitimately-scriptable host
  (`drops.dagstuhl.de`) whose `robots.txt` only disallows a few API/
  metadata paths, none of which cover the actual file downloads. Used
  that instead. Real files in hand:
  - `data/dblp.dtd` (13 KB) — downloaded in full, from
    `drops.dagstuhl.de/storage/artifacts/dblp/xml/2023/dblp-2023-06-28.dtd`.
  - `data/dblp.xml.gz` — the real September 2026 monthly release
    (`dblp-2026-09-01.xml.gz`, 1,099,942,087 bytes per the server's own
    `Content-Length`), downloading now in the background; slow on this
    machine's network, partial so far.
- `jobs/dblp_xml.py`: the shared constant-memory streaming reader (DATA-1),
  used by both the profiler and (later) the ETL job so the two never
  drift. **Real bug found and fixed while building this**: `lxml`'s
  `iterparse` (v6.1.3) has no `parser=` argument at all, and a custom
  `Resolver` registered on the global default parser is never consulted
  for iterparse's own internal DTD loading — both are dead ends. What
  actually works, confirmed by direct experiment: `load_dtd=True` +
  `resolve_entities=True` alone, with a file literally named `dblp.dtd`
  sitting next to the `.xml.gz` on disk — libxml2 resolves the DOCTYPE's
  relative `SYSTEM "dblp.dtd"` against the `.xml.gz`'s own on-disk path.
  This is exactly the proposal's own DATA-1 wording ("keeping dblp.dtd
  next to it") taken literally, not a workaround.
- `jobs/profile_dblp.py`: DATA-2 through DATA-6 all implemented — type/
  year counts, field completeness, authors-per-paper and papers-per-author
  distributions (keyed by dblp's own `pid` attribute when present, falling
  back to name text), top-50 venue prefixes, homonym-suffix and `pid`-
  coverage checks for DATA-5, and a `suggest_data_scope()` heuristic for
  DATA-6 that greedily ranks venues by paper count per candidate start
  year until the 300k–800k target band is hit.
  **Two more real bugs found via the unit tests, both fixed**: `proceedings`
  records (venue containers, not authored papers) were being counted into
  the author/field-completeness/authors-per-paper stats, dragging down
  "% records with an author" for no real reason; and `www` (person) record
  keys like `homepages/1/1000` were leaking into the venue-prefix ranking
  meant for real venues like `conf/kdd`. Both fixed by giving `proceedings`
  and `www` their own explicit branches in `profile()` instead of falling
  through the generic path.
- `jobs/tests/test_profile_dblp.py`: 11 unit tests against a small,
  hand-written synthetic fixture (`jobs/tests/fixtures/sample.xml` +
  `sample.dtd`) covering every DATA-2..6 stat, entity resolution, the
  proceedings/www exclusions above, and the `--limit` dev flag.
  **11/11 passing.**

**What's not done yet:** the real `dblp.xml.gz` download has to finish,
then the profiler needs to actually run against it (inside the `jobs`
container, matching how it will really be used) to produce
`reports/dblp_profile.md` and a concrete, evidence-based `DATA_SCOPE`
decision. Nothing here is guessed yet — DATA-6 only gets written once the
real numbers exist.
