# DBLP Explorer: Technical Proposal

Sep 27, 2026 · @Abbass

## 1. Executive summary

We propose **DBLP Explorer**, a website that turns the dblp computer science bibliography into an interactive knowledge graph. Visitors can explore it, rank it, and ask it questions in plain language.

The whole system ships as a **Docker Compose** stack. dblp is loaded into **PostgreSQL**, which is the single source of truth: relational tables for the dashboard, edge tables for the graph, and pgvector embeddings for the chatbot. Four services sit on top of it:

1. **Dashboard.** KPI tiles and charts: publications per year, top venues, top authors, and team-size trends, all read from SQL views.
2. **Graph-theory graphs.** Interactive network views built from PostgreSQL edge tables: co-authorship networks, author–paper bipartite graphs, venue similarity and community clusters.
3. **Centrality analysis.** We rank authors with two measures taken from the literature, **PageRank** (Brin & Page, 1998) and **betweenness centrality** (Freeman, 1977). Scores are computed in a batch job and stored back in PostgreSQL.
4. **RAG chatbot.** A retrieval-augmented assistant answers questions such as "Who are the most central authors in graph neural networks since 2020?" It grounds every answer in retrieved dblp records and cites them.

**Target users:** students looking for supervisors, researchers mapping a field, and committees or departments reviewing research output.

**Scope for v1:** a filtered subset of about 500k papers (for example, AI, databases and data mining venues from 2010 onward). The pipeline is designed to scale to the full dump later.

## 2. The dataset: dblp

dblp is an open bibliography of computer science run by Schloss Dagstuhl. As of 2023 it listed more than 6.5 million publications by more than 3 million authors, and it grows by more than 500,000 publications a year ([Dagstuhl](https://www.dagstuhl.de/en/dblp)). Michael Ley founded it at the University of Trier in 1993 ([Wikipedia](https://en.wikipedia.org/wiki/DBLP)). The metadata is released under CC0, so it can be reused without restriction.

**Ways to access it:**

| Channel | Format | Use in this project |
| --- | --- | --- |
| XML dump (`dblp.xml.gz` + `dblp.dtd`) | One XML file, updated monthly | Main source for building the graph |
| Search API (`/search/publ/api`, `/search/author/api`, `/search/venue/api`) | JSON / XML | Live lookups and incremental updates |
| RDF dump + SPARQL endpoint | RDF / N-Triples | Optional: links to ORCID and Wikidata |
| Semantic Scholar / OpenAlex (external) | JSON | Abstracts and citation edges, which dblp mostly lacks |

**Record types in the XML:** `article` (journal papers), `inproceedings` (conference papers), `proceedings`, `book`, `incollection`, `phdthesis`, `mastersthesis`, and `www` (author homepage records that carry name aliases).

**Key fields per record:** `key` (a unique ID such as `conf/kdd/SmithL21`), `author` (ordered, with an optional ORCID attribute), `title`, `year`, `journal` or `booktitle`, `volume`, `pages`, `ee` (DOI or URL) and `crossref` (links a paper to its proceedings).

**Two gaps to plan for:** dblp holds **no abstracts** and only **sparse citation links**. We fill both by joining on DOI with OpenAlex or Semantic Scholar, which gives the chatbot text to embed and gives PageRank a citation graph to run on.

## 3. PostgreSQL database and graph data

We load dblp into PostgreSQL 16 and model the graph *inside* it: nodes are tables and edges are join tables. The dashboard, graph service, centrality job and chatbot all read the same database, so there is no second store to keep in sync.

### 3.1 Relational schema

```sql
-- Nodes
CREATE TABLE author (
  author_id   SERIAL PRIMARY KEY,
  name        TEXT NOT NULL,
  orcid       TEXT,
  dblp_pid    TEXT UNIQUE            -- from <www> person records
);
CREATE TABLE venue (
  venue_id    SERIAL PRIMARY KEY,
  key_prefix  TEXT UNIQUE,           -- e.g. conf/kdd, journals/tkde
  name        TEXT,
  type        TEXT CHECK (type IN ('conference','journal','other'))
);
CREATE TABLE paper (
  paper_id    SERIAL PRIMARY KEY,
  dblp_key    TEXT UNIQUE NOT NULL,  -- e.g. conf/kdd/SmithL21
  title       TEXT NOT NULL,
  year        SMALLINT,
  type        TEXT,                  -- article, inproceedings, ...
  venue_id    INT REFERENCES venue,
  doi         TEXT,
  abstract    TEXT                   -- enriched from OpenAlex
);

-- Edges
CREATE TABLE authorship (             -- Author -[AUTHORED]-> Paper
  author_id   INT REFERENCES author,
  paper_id    INT REFERENCES paper,
  position    SMALLINT,              -- author order
  PRIMARY KEY (author_id, paper_id)
);
CREATE TABLE citation (               -- Paper -[CITES]-> Paper
  citing_id   INT REFERENCES paper,
  cited_id    INT REFERENCES paper,
  PRIMARY KEY (citing_id, cited_id)
);

-- Derived graph: weighted co-authorship (undirected, a < b)
CREATE MATERIALIZED VIEW coauthor_edge AS
SELECT a1.author_id AS src, a2.author_id AS dst,
       COUNT(*) AS weight, MIN(p.year) AS first_year, MAX(p.year) AS last_year
FROM authorship a1
JOIN authorship a2 ON a1.paper_id = a2.paper_id AND a1.author_id < a2.author_id
JOIN paper p ON p.paper_id = a1.paper_id
GROUP BY 1, 2;

-- Results written back by the centrality job
CREATE TABLE author_metrics (
  author_id   INT PRIMARY KEY REFERENCES author,
  degree      INT,
  pagerank    DOUBLE PRECISION,
  betweenness DOUBLE PRECISION,
  community   INT,
  computed_at TIMESTAMPTZ DEFAULT now()
);

-- Chatbot embeddings (pgvector)
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE paper_embedding (
  paper_id    INT PRIMARY KEY REFERENCES paper,
  embedding   vector(768)
);
CREATE INDEX ON paper_embedding USING hnsw (embedding vector_cosine_ops);
```

We also add B-tree indexes on `paper(year)`, `paper(venue_id)` and `authorship(paper_id)`, plus a GIN full-text index on `paper.title` for keyword search.

### 3.2 The graphs we derive

| Graph | Nodes | Edges | Weight | Used for |
| --- | --- | --- | --- | --- |
| Co-authorship | Authors | Wrote a paper together | Number of joint papers | Centrality, communities, network view |
| Author–paper | Authors + papers | AUTHORED | Author position | Ego view, chatbot graph lookup |
| Citation | Papers | CITES (directed) | — | Paper PageRank |
| Venue similarity | Venues | Share authors | Jaccard overlap of author sets | Venue landscape map |

### 3.3 ETL pipeline (the `etl` container)

1. **Download** `dblp.xml.gz` and `dblp.dtd` (monthly).
2. **Stream-parse** with `lxml.iterparse`, resolving the DTD's HTML entities. This takes constant memory, even though the file is several GB.
3. **Filter** to the v1 scope (venue list × year ≥ 2010).
4. **Bulk load** with PostgreSQL `COPY` from CSV into `author`, `venue`, `paper` and `authorship`.
5. **Enrich** by DOI from OpenAlex, adding abstracts and the `citation` table.
6. **Refresh** `coauthor_edge`, then trigger the centrality and embedding jobs.

The graph can also be exported as plain edge lists for Gephi or NetworkX:

```csv
src,dst,weight,first_year,last_year
101,202,5,2014,2021
101,305,2,2019,2020
202,305,1,2020,2020
```

## 4. Dashboard and graph-theory visualizations

The site has two visual services. The **Dashboard** answers "how much, and when?" with statistical charts. The **Graph Explorer** answers "who is connected to whom?" with node-link diagrams. Each view below is tied to one question.

### 4.1 Dashboard (statistical charts)

| View | Question it answers | Chart type | SQL source |
| --- | --- | --- | --- |
| Publications per year | How fast is CS publishing growing? | Line chart, one line per type (journal vs conference) | `paper` grouped by year, type |
| Top venues | Which conferences and journals publish most? | Horizontal bar, filterable by year | `paper` ⋈ `venue` |
| Team size over time | Are papers getting more co-authors? | Box plot or median line with an IQR band per year | `authorship` count per paper |
| Productivity distribution | How skewed is output per author? | Log-log histogram (a long tail is expected) | `authorship` count per author |
| Topic trends | Which keywords are rising? | Heatmap: keyword × year | title keyword extraction |
| Author career | How has one author's output evolved? | Stacked bars by venue type + co-author count line | `authorship` for one author |
| KPI tiles | What is in the database now? | Stat tiles: papers, authors, venues, last update | `COUNT(*)` views |

### 4.2 Graph Explorer (graph theory)

| View | What it shows | Graph encoding | Graph concept |
| --- | --- | --- | --- |
| **Co-authorship network** | Collaboration clusters in a field | Node size = PageRank, colour = community, edge width = joint papers | Weighted undirected graph |
| **Ego network** | One author's circle, 1–2 hops out | Radial layout with the author at the centre | Neighbourhood, k-hop subgraph |
| **Community map** | Research groups found automatically | Nodes coloured by Louvain community, with a legend of top keywords per group | Modularity, community detection |
| **Bridge view** | Authors who connect separate groups | Top betweenness nodes highlighted, other nodes faded | Betweenness, structural holes |
| **Shortest path** | "How am I connected to X?" (an Erdős-number-style query) | Path highlighted between two chosen authors | BFS / Dijkstra |
| **Author–venue bipartite** | Who publishes where | Two columns, authors on the left and venues on the right | Bipartite graph |
| **Venue similarity map** | Which venues share a community | Force layout of venues, edges by Jaccard overlap | Projection of a bipartite graph |
| **Network over time** | How collaboration grew | Year slider that adds edges by `first_year` | Temporal graph |
| **Degree distribution** | Whether the network is scale-free | Log-log scatter of P(k) against k | Power law (Newman, 2001) |

**Rendering rules:** the browser draws at most about 2,000 nodes at once, using Sigma.js on WebGL. Larger graphs are filtered first (by venue, year and top-N by PageRank) or laid out on the server in advance. Clicking a node opens that author's profile and centrality scores.

## 5. Centrality measures from the literature

We use two measures that answer different questions. **PageRank** asks who is *influential*: connected to other well-connected people. **Betweenness** asks who is a *bridge*: sitting on the paths between groups. A researcher can score high on one and low on the other, which is why we show both.

### 5.1 PageRank (Brin & Page, 1998)

**Source paper:** S. Brin and L. Page, "The anatomy of a large-scale hypertextual Web search engine," *Computer Networks and ISDN Systems*, 30(1–7), 107–117, 1998.

**Idea:** a node is important if important nodes point to it. Picture a random walker who follows edges and, with probability 1 − d, jumps to a random node. PageRank is the share of time the walker spends at each node.

```latex
PR(v) = \frac{1-d}{N} + d \sum_{u \in N(v)} \frac{w_{uv}}{\sum_{x \in N(u)} w_{ux}} \, PR(u)
```

Here N is the number of nodes, d is the damping factor (0.85), N(v) is the set of v's neighbours, and w is the edge weight (number of joint papers).

**How it has been applied to scholarly data:** Liu et al. (2005) proposed *AuthorRank*, a weighted PageRank on a co-authorship network of the digital library community. Ding et al. (2009) ranked authors with PageRank on co-citation networks.

**Our use:**

- **Author PageRank** on the weighted `coauthor_edge` graph.
- **Paper PageRank** on the directed `citation` graph (a paper cited by influential papers ranks high).
- **Computation:** power iteration until the change is below 1e-6. Cost is O(E) per iteration and it converges in about 50 iterations, so it runs in minutes even on millions of edges.

### 5.2 Betweenness centrality (Freeman, 1977)

**Source paper:** L. C. Freeman, "A set of measures of centrality based on betweenness," *Sociometry*, 40(1), 35–41, 1977.

**Idea:** a node is central if many shortest paths between other nodes pass through it. These are the people who connect otherwise separate research communities.

```latex
C_B(v) = \sum_{s \neq v \neq t} \frac{\sigma_{st}(v)}{\sigma_{st}}
```

Here σ\_st is the number of shortest paths from s to t, and σ\_st(v) is how many of them pass through v. We normalise by (n − 1)(n − 2) / 2 so scores fall between 0 and 1.

**Computing it:** Brandes (2001) gave the standard algorithm, which runs in O(nm) time on unweighted graphs. That is still too slow for millions of authors, so we use **sampled Brandes**: start shortest-path searches from k random source nodes (k ≈ 1,000) and scale up. This is `betweenness_centrality(G, k=1000)` in NetworkX, or the faster equivalents in igraph and NetworKit. For weighted betweenness, the distance is 1 / weight, so frequent collaborators count as closer.

**How it has been applied to scholarly data:** Newman (2001) computed betweenness on co-authorship networks from physics, biomedicine and computer science. He showed that a few authors act as the main bridges between fields.

### 5.3 How the website uses them

| Where | What the user sees |
| --- | --- |
| Author profile | PageRank and betweenness as percentiles ("top 2% influence, top 10% bridge") |
| Leaderboards | Top-50 tables per field and year range, sortable by either measure |
| Graph Explorer | Node size = PageRank, and a "show bridges" toggle that highlights high-betweenness nodes |
| Influence × bridge scatter | PageRank on x, betweenness on y. Four quadrants: hub, bridge, both, peripheral |
| Chatbot | Can answer "who are the bridges between databases and ML?" from `author_metrics` |

The centrality job runs nightly, or after each ETL refresh. It reads `coauthor_edge` and `citation`, computes both scores with igraph, and writes them to `author_metrics`.

## 6. RAG chatbot

The chatbot answers questions about dblp in plain language, and every fact in an answer comes from a record it retrieved from PostgreSQL. It never answers from the LLM's memory. If the tools find nothing, it says so.

### 6.1 What "RAG" means here, in one paragraph

Retrieval-Augmented Generation (Lewis et al., 2020) works in two steps. First, **retrieve**: search our database for the records relevant to the question. Second, **generate**: give those records to an LLM and ask it to answer using only them, citing each one. This stops the LLM from inventing papers, which LLMs often do with bibliographic questions.

### 6.2 How a question flows

[embedded content: RAG chatbot · query-time flow · 3 retrieval tools]

The router picks tools by question type, and one question can use more than one tool. For example, "central authors in GNNs" uses semantic search to find GNN papers, then the graph tool to rank their authors.

### 6.3 Offline indexing (run by the `embedder` container)

1. **Build one text chunk per paper:** `title + venue + year + authors + abstract` (the abstract comes from the OpenAlex enrichment; the title alone is the fallback).
2. **Embed** each chunk with an open embedding model served locally, for example `nomic-embed-text` (768 dimensions) through Ollama, or a sentence-transformers model.
3. **Store** the vectors in `paper_embedding` (pgvector) with an HNSW index.
4. **Re-embed** only new or changed papers after each monthly ETL run.

### 6.4 The three retrieval tools

| Tool | What it does | Example question | Safety |
| --- | --- | --- | --- |
| `semantic_search(query, year_from?, venue?)` | Embeds the query and returns the top-10 papers by cosine similarity, with optional SQL filters | "Recent papers on retrieval-augmented generation" | Read-only |
| `sql_query(template, params)` | Runs one of about 15 parameterised SQL templates (top authors in a venue, papers per year, an author's co-authors) | "How many papers did VLDB publish in 2023?" | Templates only, a read-only DB role, 5 s timeout |
| `graph_query(kind, params)` | Reads `author_metrics` and runs shortest-path or ego-network queries | "Who are the top bridge authors in data mining?" | Read-only, max 3 hops |

We use fixed SQL templates rather than free text-to-SQL in v1, because they are safer and easier to test. Free text-to-SQL can be added later against a restricted read-only view.

### 6.5 Prompt template

```text
SYSTEM: You answer questions about the dblp computer science bibliography.
Use ONLY the records in <context>. Cite each fact with its [dblp_key].
If the context does not contain the answer, say you could not find it.

<context>
[conf/kdd/SmithL21] "Title..." (KDD 2021) authors: ... abstract: ...
[author_metrics] Jane Doe: pagerank=0.0041 (top 1%), betweenness=0.012
</context>

USER: {question}
```

### 6.6 Example conversation

| User asks | Tools used | What the bot returns |
| --- | --- | --- |
| "Who are the most influential authors in graph neural networks since 2020?" | semantic search → graph tool | A ranked list of 10 authors with PageRank percentiles, each linked to 2–3 supporting papers |
| "Summarise what Jane Doe works on." | SQL (her papers) → semantic (abstracts) | A 3-sentence summary citing her top papers by key |
| "How am I connected to Yoshua Bengio?" | graph tool (shortest path) | The co-author chain, with the joint paper for each hop |
| "How many ICSE papers were there in 2022?" | SQL template | One number, with the query shown as provenance |

### 6.7 Tech choices

- **Orchestration:** LangChain or LlamaIndex tool-calling agent in the FastAPI `chatbot` service.
- **LLM:** a pluggable interface. Use a hosted API for quality, or a free local model in Ollama (`qwen3.5:9b`, see §8.5) when everything must stay offline in Docker.
- **Memory:** the last 5 turns, so follow-up questions such as "and in 2023?" work.
- **UI:** a chat panel whose answers carry clickable citations. A citation opens the paper, or highlights the author in the Graph Explorer.

### 6.8 How we evaluate it

- **Test set:** 100 hand-written questions with known answers (40 factual SQL, 30 topical, 30 graph).
- **Metrics:** retrieval recall@10, answer accuracy, citation precision (the share of cited keys that really support the claim), and hallucination rate (the target is 0 invented papers). We also use the RAGAS faithfulness score.
- **Latency target:** under 5 s per answer on the local stack.

### 8.0 Task 0: inspect the dataset first

Before writing the schema in code, run `jobs/profile_dblp.py` on the real `dblp.xml.gz` and save `reports/dblp_profile.md`.

- **DATA-1** Stream the file with `lxml.etree.iterparse(load_dtd=True)`, keeping `dblp.dtd` next to it. The DTD defines entities such as `&uuml;`, and parsing fails without it.
- **DATA-2** Count records per type (`article`, `inproceedings`, `proceedings`, `book`, `incollection`, `phdthesis`, `mastersthesis`, `www`) and per year.
- **DATA-3** For each field, report the share of records that have it: `author`, `year`, `ee` (DOI), `crossref`, and ORCID on authors.
- **DATA-4** Report the distribution of authors per paper and papers per author, and the top 50 venue key prefixes (`conf/kdd`, `journals/tkde`, ...).
- **DATA-5** Check author disambiguation. dblp adds a 4-digit suffix to homonyms ("Wei Wang 0001"), and `www` records list aliases. Map every alias to one `dblp_pid`.
- **DATA-6** Use the report to choose `DATA_SCOPE`, the venue list and start year in `.env`. Aim for roughly 300k–800k papers in v1, and adjust the schema if the profile shows surprises.

### 8.4 Service D: Centrality measures (`jobs/centrality.py` + page `/rankings`)

- **CENT-1** Load `coauthor_edge` into an igraph `Graph` (undirected, weighted).
- **CENT-2** PageRank: `g.pagerank(weights='weight', damping=0.85)`.
- **CENT-3** Betweenness: use `g.betweenness(cutoff=...)`, or sampled Brandes with k = 1,000 sources, with distance = 1 / weight. Normalise to between 0 and 1.
- **CENT-4** Degree, and Louvain communities via `g.community_multilevel(weights='weight')`.
- **CENT-5** Paper PageRank on the directed `citation` graph, stored in `paper_metrics`.
- **CENT-6** Upsert everything into `author_metrics` with `computed_at`, plus a percentile column for each measure.
- **CENT-7** The `/rankings` page has two sortable top-50 tables (PageRank and betweenness), filterable by venue and years. Below them sits the influence × bridge scatter, with PageRank percentile on x and betweenness percentile on y.
- **CENT-8** An "About these measures" panel that explains both measures in 2 lines each and cites Brin & Page (1998) and Freeman (1977).
- **Accept:** the job finishes in under 30 min on v1, and the top-10 lists look plausible when a person spot-checks them against well-known researchers in the chosen field.

### 8.5 Service E: RAG chatbot (page `/chat`)

**Recommended free LLM: `qwen3.5:9b` in Ollama.** It runs locally in the `ollama` container, costs nothing per query, and the Qwen3 family is trained for function calling, which the three tools need ([Morph, Aug 2026](https://www.morphllm.com/best-ollama-models)). It needs about 12 GB of VRAM. On an 8 GB GPU or CPU only, use `qwen3:8b` or a smaller quantisation. Keep the model name in `OLLAMA_MODEL` so it can be swapped without code changes.

**Embeddings: `nomic-embed-text` in Ollama** (a 274 MB download, 768 dimensions, which matches `vector(768)` in §3.1).

- **CHAT-1** `embed.py` builds a chunk per paper (§6.3), embeds it in batches of 64, and writes to `paper_embedding`.
- **CHAT-2** Implement the three tools in §6.4 as Python functions with JSON schemas, called through Ollama's OpenAI-compatible `/v1/chat/completions` with `tools`.
- **CHAT-3** An agent loop of at most 4 tool calls per question, then a final answer that uses the prompt in §6.5.
- **CHAT-4** Stream tokens to the UI with Server-Sent Events: `POST /api/chat` returns `text/event-stream`.
- **CHAT-5** The response carries `citations[]` (dblp keys and author IDs), which the UI renders as chips. A paper chip links to `https://dblp.org/rec/{key}`, and an author chip opens the Graph Explorer ego view.
- **CHAT-6** Validate every cited key against the database before sending. Drop any key that does not exist, and log it as a hallucination.
- **CHAT-7** Put the 100-question test set in `api/tests/chat_eval.jsonl` and run it with `pytest -m eval`.
- **Accept:** citation precision is 90% or higher, no invented keys reach the user, and the first token arrives in under 3 s on GPU.

Keep it calm and academic: a neutral canvas, one indigo accent, and colour used only when it means something. All colours live as CSS variables, so light and dark mode come free and the charts read the same tokens.

### 9.3 Chart rules (dashboard)

## 10. Build order and risks

Give Claude Code one milestone at a time, and check its acceptance criteria before moving on.

1. **M0 – Skeleton:** repo layout, `docker-compose.yml`, DB schema, empty FastAPI and React apps. `docker compose up` shows a blank sidebar app.
2. **M1 – Data:** Task 0 profiling report, then ETL (DATA-1 to DATA-6, DB-1 to DB-4). OpenAlex enrichment can run in the background.
3. **M2 – Dashboard:** DASH-1 to DASH-7, with the style guide applied from the start.
4. **M3 – Centrality:** CENT-1 to CENT-8. This must land before the graph work, because the Graph Explorer sizes nodes by PageRank.
5. **M4 – Graph Explorer:** GRAPH-1 to GRAPH-7.
6. **M5 – Chatbot:** CHAT-1 to CHAT-7, then the evaluation run.
7. **M6 – Polish:** author page, dark mode, README with setup steps, seed script for a small demo dataset.

| Risk | Impact | Mitigation |
| --- | --- | --- |
| The full dump is too big for a laptop | ETL and betweenness become slow | Use the v1 scope filter, sampled betweenness, and a `DEMO=1` mode with about 20k papers |
| Author name ambiguity | Wrong collaboration edges | Use dblp person IDs (`www` records) rather than raw names |
| No abstracts in dblp | Weak semantic search | OpenAlex enrichment, with title + venue + authors as the fallback chunk |
| A local LLM is slow without a GPU | Chat latency above 10 s | Use a smaller quantisation, or point `OLLAMA_URL` at a free hosted endpoint |
| The LLM invents papers | Loss of trust | Tool-only context, plus key validation (CHAT-6) |
| Browser freezes on big graphs | Unusable Graph Explorer | Hard cap of 2,000 nodes, top-N filtering, layout in a web worker |
